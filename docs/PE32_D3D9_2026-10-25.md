# PE32 graphics routing: startup boundary and experimental candidate

## Observed failures on the actual Tab S11

HL2's installed Linux executable is ELF32/i386. Steam automatically chose Valve
FEX + scout-on-soldier. The process exited before a window because FEX could not
connect to the per-prefix FEXServer socket. Selecting the existing DroidDeck FEX
tool advanced past that failure but reproduced the previously isolated
`sbrk() failure while processing tunables` loader failure. That is not evidence
of a Vulkan/Mavk defect. The earlier native x86-64 `true` reproducer remains
relevant; no new broad FEX investigation was started.

The standard Steam compatibility selection was then changed to the existing
DroidDeck ARM64 Proton. Steam reused the content and downloaded about 66 MB of
Windows platform files. The Windows executable is PE32/i386, not AMD64.
Proton reached D3D9 device enumeration through Winevulkan and found Mali-G925.
Its stock **x86 DXVK 3.1.1** rejected the device because `fillModeNonSolid` is
missing. The existing Mavk payload intentionally replaces only ARM64X
D3D10core/D3D11/DXGI, leaving PE32 and D3D9 stock. Thus successful ARM64/AMD64
Muck rendering did not establish support for this architecture/API combination.

## General candidate, not an application exception

`adapters/droiddeck/proton_d3d11.py` accepts an optional absolute
`MAVK_SAREK_I386_PAYLOAD` directory containing independently PE-machine-validated
`d3d9.dll` and `dxgi.dll`. Only Proton's **32-bit** copies of these libraries are
routed there. ARM64X D3D11 selection is unchanged, as are stock paths when the
option is absent. PE32 D3D11 remains unsupported by Mavk. No application IDs,
executable-name rules, game configuration or fictional Vulkan features were added.

The candidate builds the existing reviewed Sarek source for i686 with D3D9,
instead of changing game code or lying about the Mali feature bits. This remains
the same experimental consumer with the documented nullDescriptor diagnostic
admission; it is not upstream DXVK compatibility or Vulkan conformance.

Build helper: `experiments/droiddeck/build-sarek-i386.sh`. It copies existing
source to C:, uses the existing compiler/tools read-only, and places all new
build outputs on C:. The legacy machine-specific tool paths are explicit;
portable dependency packaging is still required before publication.

General routing regressions: `python experiments/droiddeck/test-proton-payload-selection.py`
checks opt-in PE32 D3D9/DXGI, unchanged ARM64/stock selection and rejection of
relative/missing payloads. These are routing tests, not GPU rendering tests.

## Status / rollback

PE32 build completed (248 targets), both DLLs passed actual PE-machine checks.
The real launch created a D3D9 device on Mali, then failed mapping4MiB buffers
with VK_ERROR_OUT_OF_HOST_MEMORY. Enabling the **existing**, separately opted-in
DroidDeck placed-memory layer (after verifying both mapping-lock API symbols on
this device) mapped4/8/16MiB allocations below4GiB and reached a visible Valve
intro. This is measured G925 progress, not reliance on a G715 result alone.
Native-alias placement is experimental, not a new unsafe physical-memory reader.

After the intro, a real common shader-policy defect appeared: static-use
validation rejected a push-constant structure containing vec3 members at offsets
0 and12 although the application enabled native scalarBlockLayout. Track that
enabled feature from either Vulkan12Features or its dedicated feature structure,
and pass it consistently to input/output/optimizer/static-use and optional UBO
validation. The strict default remains false; no driver feature is fabricated.
A scalar-layout admission/rejection regression accompanies the correction.

On2026-10-26 the user confirmed actual HL2 gameplay at the panel resolution,
approximately15FPS by observation. This is user-reported gameplay, not an
independently captured FPS benchmark. Changing resolution in-game crashed HL2
and left Steam unresponsive. A fresh session was configured at1920x1080 and
the same existing Windows route launched with `-w1920 -h1080 -fullscreen` for
the user's recording. Actual D3D9 presentation parameters and Vulkan swapchain
both confirmed1920x1080 (60Hz display mode, not a60FPS claim).
No further FPS optimization was undertaken.
Installed source APK6c8680f5 and its runtime remain untouched.
The candidate is staged separately under app-private `files/mavk-pe32-test`.
Temporary launch logging/configuration has a byte-for-byte backup at guest
`/tmp/mavk-hl2-env.before`; restore it after the experiment. Compatibility tool
selection can be restored to Steam native default; this will require Steam to
restore its platform binaries. No user/account/save data was reset.

## Confirmed gameplay and packaged-launch work (2026-10-26)

User confirmed actual Full HD gameplay:10–30FPS near maximum settings, usually
20–30, and30–50FPS on low. Rare character pauses/repeated sound remain. This is
user observation, not an independent FPS benchmark. Passive compositor telemetry
recorded177 GPU game buffers=177 zero-copy buffers in one10s interval, CPU copy0
and pool drops0; the sampled interval is not a universal gameplay score.

Packaged candidate contains automatic PE32 Sarek selection and architecture-gated
WoW64 placement; no game-name/appid fix. Opted-in Mavk sessions prefer Proton
for dual-platform x86 titles, preserving explicit tools and ARM64 native apps.
Final ordinary-button APK verification awaits the end of the recording session.

Private layer overrides must retain the packaged hybris directory after the
candidate directory. Omitting it selected the old system compatibility layer;
that early failure was not proof against the scalar-layout correction. The
existing general helper preserves the complete stack. Specialization-only alias
checks pass, but some D3D9 live aliases still reject; do not claim complete support.
